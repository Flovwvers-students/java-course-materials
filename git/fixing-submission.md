# Git: как исправить состав сдачи и отправить обновление

Этот порядок включать в конец каждого отзыва. Это инструкции студенту, а не разрешение агенту менять репозиторий. Текст адаптировать к проверенным путям и обнаруженной проблеме.

## Как исправить и отправить изменения

Работайте в **той же ветке, из которой открыт этот PR**, и исправьте код и README по замечаниям.

### Если Git сообщает о конфликте

1. Посмотрите `git status` и откройте **каждый конфликтный исходник или README** в редакторе. Файл сообщения коммита, который может открыть Git, — другое окно: в нём пишется сообщение, а конфликт устраняется в самих исходниках/README.
2. Найдите каждый блок вида:

```text
<<<<<<< подпись первой версии
первый вариант фрагмента
=======
второй вариант фрагмента
>>>>>>> подпись второй версии
```

3. Сравните варианты и составьте правильный итоговый фрагмент: оставьте подходящий вариант либо вручную согласуйте нужные части обоих. Удалите ненужный код, все строки `<<<<<<<`, `=======`, `>>>>>>>` вместе с подписями. Если есть блок общего предка с `|||||||`, он тоже служебный и не должен остаться. В итоговом файле должна быть одна согласованная реализация без случайных дубликатов; остальной нужный код сохраните.
4. Сохраните все файлы, проверьте отсутствие маркеров поиском по проекту, соберите программу в чистый каталог и выполните тесты. `git diff --check` дополнительно проверит изменённые строки, но не заменяет поиск и сборку. После исправления отметьте конкретные файлы через `git add -- путь/к/файлу` и снова посмотрите `git status`.
5. Завершите операцию, указанную в `git status`: при незавершённом merge — `git merge --continue`, при rebase — `git rebase --continue`. После конфликта при `stash apply/pop` отдельной команды «continue» нет: исправленные и добавленные файлы сохраняются обычным коммитом. Если конфликтные маркеры уже были закоммичены и активного merge/rebase нет, исправьте их новым обычным коммитом. Не запускайте `merge --continue` просто из-за наличия маркеров в файле.

### После исправления

Соберите загруженную версию и выполните проверки. Посмотрите `git status` и изменения перед коммитом; включайте только нужные файлы. Если активной операции merge/rebase нет, сохраните исправления новым коммитом. Выполните push в эту же ветку.

**Существующий PR автоматически подтянет новые коммиты. Новый PR создавать не нужно.** Откройте PR и проверьте, что последний коммит появился и исправленные файлы отображаются правильно. Напишите, что исправлено по каждому замечанию и какими тестами проверено, затем запросите **Re-request review**, если кнопка доступна; иначе оставьте комментарий преподавателю с просьбой перепроверить. Дождитесь проверки, не закрывайте PR и не нажимайте Merge.

## Уже отслеживаемый результат сборки

При наличии такого замечания включить перед общим порядком конкретные команды с проверенным путём. Пример для lab-01/src/01:

**Как исправить отслеживаемый файл:** в корне локального репозитория, находясь в ветке этого PR, выполните:

```sh
git rm --cached -- lab-01/src/01
git add -- .gitignore
git diff --cached --stat
```

`git rm --cached` убирает файл из отслеживания в следующем коммите, **сохраняя его на вашем диске**. В подготовленных изменениях должно быть удаление `lab-01/src/01`; исходник `01.cpp` должен остаться. Если Git сообщает об ошибке, сначала разберите её; добавлять `-f` не требуется.

После проверки остальных исправлений сохраните изменения коммитом и отправьте в ту же ветку, например:

```sh
git commit -m "Remove tracked build artifact"
git push
```

Проверьте `git ls-files -- lab-01/src/01`: команда не должна вывести этот путь. На GitHub откройте последнюю версию ветки/PR — исполняемого файла там быть не должно. Старые коммиты могут хранить прежнюю копию: для этой сдачи переписывать историю не нужно. Запись в `.gitignore` сохраните, чтобы результат сборки не добавился снова. Сам ELF я не запускал.
