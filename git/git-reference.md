# Git, GitVerse и GitHub: практическое руководство для студентов

**Git** — система контроля версий, она работает на вашем компьютере. **GitVerse** и **GitHub** — это сервисы, где хранятся репозитории и ведётся совместная работа. Основная часть документа (команды Git, ветки, коммиты, конфликты) одинакова для обоих сервисов. Различия в том, как создаётся аккаунт, как настраивается доступ и как называются и выглядят pull request'ы, задачи и автоматическая сборка.

- **GitVerse** — российская платформа от СберТеха (дочерняя компания Сбера): репозитории, pull request'ы, задачи, CI/CD, импорт с других площадок, ИИ-помощник GigaCode.
- **GitHub** — самая распространённая в мире платформа (принадлежит Microsoft): огромное число открытых проектов, GitHub Actions, ИИ-помощник Copilot.

Умение работать с одним сервисом переносится на другой почти целиком, так что учитесь на том, который требует курс, а ниже смотрите, чем они отличаются.

> Интерфейсы платформ обновляются, названия кнопок могут слегка отличаться. Если что-то не нашли, смотрите документацию на gitverse.ru и docs.github.com.

## 1. Что такое Git и зачем он нужен

Git — система контроля версий. Она хранит историю изменений проекта и позволяет:

- откатиться к любой прошлой версии;
- работать над одним проектом вдвоём и больше без хаоса в файлах;
- пробовать эксперименты в отдельных ветках;
- сдавать работу преподавателю одной ссылкой.

**Главная модель:**

```
рабочая папка  --git add-->  индекс (staging)  --git commit-->  локальный репозиторий  --git push-->  GitVerse
```

- **Рабочая папка** — ваши файлы.
- **Индекс** — то, что войдёт в следующий коммит.
- **Коммит** — снимок проекта с автором, временем и сообщением.
- **Удалённый репозиторий (remote)** — копия на GitVerse.

## 2. Установка и первичная настройка

Установите Git: [https://git-scm.com](https://git-scm.com) (Windows), `sudo apt install git` (Ubuntu), `brew install git` (macOS).

Один раз укажите, кто вы:

```bash
git config --global user.name "Фамилия Имя"
git config --global user.email "ваша_почта@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf input     # Linux/macOS
git config --global core.autocrlf true      # Windows
```

Проверка:

```bash
git config --list
```

Почта должна совпадать с той, что привязана к аккаунту GitVerse, иначе коммиты не свяжутся с профилем.

## 3. Регистрация и доступ к GitVerse и GitHub

1. Зарегистрируйтесь на нужном сервисе:
   - **GitVerse**: gitverse.ru (вход через СберID или другим способом, который предлагает платформа);
   - **GitHub**: github.com (регистрация по почте, имя пользователя станет частью адресов ваших репозиториев).
2. Настройте способ аутентификации. Есть два варианта, они одинаковы для обоих сервисов.

### Вариант А. SSH-ключ (рекомендуется)

```bash
ssh-keygen -t ed25519 -C "ваша_почта@example.com"
```

Нажмите Enter на все вопросы (или задайте пароль для ключа). Затем выведите **публичный** ключ:

```bash
cat ~/.ssh/id_ed25519.pub
```

Скопируйте содержимое и добавьте его в настройках профиля в разделе SSH-ключей (у GitHub это Settings → SSH and GPG keys). Один ключ можно добавить на оба сервиса. Проверить подключение:

```bash
ssh -T git@gitverse.ru     # GitVerse
ssh -T git@github.com      # GitHub
```

> Никогда не отправляйте и не публикуйте файл `id_ed25519` (без `.pub`). Это приватный ключ.

### Вариант Б. HTTPS и персональный токен

В настройках профиля создайте токен доступа (на GitHub он называется Personal Access Token) и используйте его вместо пароля при `git push`/`git clone` по HTTPS. Обычный пароль от аккаунта GitHub для Git по HTTPS не принимает. Токен храните как пароль: не вставляйте его в код, чаты и скриншоты.

### Удобство: GitHub CLI

Для GitHub есть консольная утилита `gh`. Она упрощает вход и работу с pull request'ами:

```bash
gh auth login        # вход через браузер
gh repo clone логин/репозиторий
gh pr create         # создать pull request из текущей ветки
gh pr list
```

## 4. Первый репозиторий

### Сценарий 1. Репозиторий создан на GitVerse, нужно скачать

1. На GitVerse нажмите создание нового репозитория, задайте имя, видимость (публичный/приватный), при желании добавьте README и `.gitignore`.
2. Скопируйте адрес клонирования и выполните:

```bash
git clone git@gitverse.ru:ваш_логин/имя_репозитория.git    # GitVerse
git clone git@github.com:ваш_логин/имя_репозитория.git     # GitHub
cd имя_репозитория
```

Точный адрес лучше брать с кнопки клонирования на странице репозитория.

### Сценарий 2. Проект уже есть на компьютере

```bash
cd путь/к/проекту
git init
git add .
git commit -m "Первый коммит"
git remote add origin git@gitverse.ru:ваш_логин/имя_репозитория.git   # или git@github.com:...
git push -u origin main
```

(`-u` запоминает связь локальной ветки с удалённой, дальше достаточно `git push`.) Пустой репозиторий на сайте нужно создать заранее, без README, иначе первый пуш может отклониться из-за расхождения историй.

### Сценарий 3. Проект лежит на другой площадке

Оба сервиса умеют **импортировать** репозиторий с других git-платформ через веб-интерфейс. Подойдёт, если нужно перенести историю целиком.

### Сценарий 4. Один проект на двух сервисах

Например, основной репозиторий на GitVerse, зеркало на GitHub. У репозитория может быть несколько удалённых адресов:

```bash
git remote add github git@github.com:ваш_логин/имя_репозитория.git
git remote -v                 # список удалённых адресов
git push github main          # отправить в конкретный remote
```

## 5. Ежедневная работа: основной цикл

```bash
git status                  # что изменилось
git diff                    # посмотреть изменения построчно
git add файл.cpp            # добавить конкретный файл в индекс
git add .                   # добавить всё (проверьте status перед этим!)
git commit -m "Сообщение"   # зафиксировать
git push                    # отправить на GitVerse
git pull                    # получить чужие изменения
git log --oneline --graph   # короткая история
```

### Как писать сообщения коммитов

Плохо: `fix`, `правки`, `asdf`, `финал v2`.

Хорошо: короткое описание того, **что и зачем** изменено:

```
Добавить проверку деления на ноль в calculator
Исправить утечку памяти при удалении узла списка
Вынести чтение файла в отдельную функцию
```

Правила: одна логическая правка = один коммит; первая строка до \~70 символов; глагол в начальной форме (добавить, исправить, удалить).

> GigaCode в GitVerse умеет генерировать названия и описания коммитов. Использовать можно, но **всегда читайте результат** и исправляйте, если он не отражает ваших изменений. Если на курсе требуется отчёт об использовании ИИ, указывайте и это.

## 6. Что нельзя коммитить: `.gitignore`

В репозиторий должны попадать исходники и конфигурация, а не результаты сборки. Создайте файл `.gitignore` **до первого коммита**.

Пример для C++-проекта:

```gitignore
# Сборка
build/
cmake-build-*/
out/
*.o
*.obj
*.exe
*.a
*.so
*.dll

# IDE
.vscode/
.idea/
*.user
.vs/

# Системное
.DS_Store
Thumbs.db
```

Если файл уже попал в историю, `.gitignore` его не уберёт. Нужно убрать из индекса:

```bash
git rm --cached путь/к/файлу
git commit -m "Убрать файл из репозитория"
```

> Пароли, токены, ключи и личные данные **никогда** не коммитим. Если случайно закоммитили секрет и отправили, считайте его скомпрометированным и перевыпустите. Удаление из следующего коммита не стирает его из истории.

## 7. Ветки

Ветка — независимая линия разработки. Основная ветка называется `main`. Для каждой задачи создаётся своя.

```bash
git switch -c feature/linked-list     # создать ветку и перейти на неё
git switch main                       # вернуться
git branch                            # список веток
git branch -d feature/linked-list     # удалить после слияния
```

Рекомендуемая схема:

1. `main` всегда содержит рабочий код.
2. Новая задача → новая ветка от свежего `main`.
3. Закончили → отправили ветку → открыли pull request → слили.

### Слияние и конфликты

```bash
git switch main
git pull
git merge feature/linked-list
```

Если Git не смог объединить правки, он пометит файл:

```
<<<<<<< HEAD
ваш вариант
=======
чужой вариант
>>>>>>> feature/linked-list
```

Что делать:

1. Откройте файл, оставьте нужный вариант (или объедините), **удалите маркеры** `<<<<<<<`, `=======`, `>>>>>>>`.
2. `git add файл`
3. `git commit` (или `git merge --continue`)

Не паникуйте: отменить слияние можно командой `git merge --abort`.

## 8. Pull request (merge request) в GitVerse и GitHub

Pull request — запрос на слияние вашей ветки в основную. Это место для **обсуждения и проверки кода**. Процесс на обоих сервисах одинаковый.

1. Отправьте ветку: `git push -u origin feature/linked-list`
2. В веб-интерфейсе создайте pull request (после пуша сайт обычно сам предлагает кнопку): источник — ваша ветка, цель — `main`. На GitHub можно из консоли: `gh pr create`.
3. Напишите заголовок и описание: что сделано, как проверить.
4. Рецензент оставляет комментарии к строкам кода.
5. Вносите правки новыми коммитами в ту же ветку, они автоматически появятся в запросе.
6. После одобрения запрос сливается, ветку можно удалить.

**Хорошее описание PR:**

```
Что сделано: реализован односвязный список (вставка, удаление, поиск).
Как проверить: собрать проект, запустить тесты из tests/linked_list_test.cpp.
Известные ограничения: итераторы пока не реализованы.
```

## 9. Issues (задачи)

И GitVerse, и GitHub включают трекер задач. Используйте его, чтобы:

- записывать баги и идеи;
- распределять работу в командном проекте;
- связывать коммиты и задачи (упоминайте номер задачи в сообщении коммита или PR, например `#12`).

Хорошая задача содержит: что ожидалось, что произошло, как воспроизвести.

## 10. Отмена и исправление ошибок

| Ситуация | Команда |
| --- | --- |
| Убрать файл из индекса (до коммита), оставив правки | `git restore --staged файл` |
| Отбросить правки в файле (**необратимо**) | `git restore файл` |
| Исправить сообщение последнего коммита (ещё не отправленного) | `git commit --amend` |
| Отменить коммит, **создав новый** «обратный» (безопасно для общих веток) | `git revert <хеш>` |
| Временно спрятать незакоммиченные правки | `git stash` / `git stash pop` |
| Найти потерянный коммит | `git reflog` |

**Опасные команды**, которые перезаписывают историю: `git reset --hard`, `git push --force`, `git rebase` на общих ветках. Если не уверены, не используйте их и спросите преподавателя.

## 11. CI/CD

Оба сервиса умеют автоматически собирать проект и запускать тесты при каждом пуше. Пайплайн описывается конфигурационным файлом внутри репозитория.

Зачем это студенту: сразу видно, что код собирается не только «у меня на компьютере», а тесты проходят.

### GitHub Actions

Файл кладётся в `.github/workflows/build.yml`. Пример для C++-проекта на CMake:

```yaml
name: build

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Настройка
        run: cmake -S . -B build
      - name: Сборка
        run: cmake --build build
      - name: Тесты
        run: ctest --test-dir build --output-on-failure
```

Результат виден на вкладке Actions и прямо в pull request'е (зелёная галочка или красный крест).

### GitVerse

У GitVerse свой формат пайплайнов. Актуальные примеры и синтаксис берите из раздела про CI/CD в документации платформы, я не стал выдумывать конфиг по памяти. Идея та же: файл в репозитории, шаги «собрать» и «запустить тесты».

## 12. Дополнительные возможности

**GitVerse**

- **GigaCode** — ИИ-ассистент: отвечает на вопросы по платформе, подсказывает код, помогает с коммитами.
- **GitVerse Pages** — публикация статических сайтов из репозитория.
- **Пакеты** — хранение и публикация пакетов для сборки.

**GitHub**

- **Copilot** — ИИ-помощник по коду в редакторе и на сайте.
- **GitHub Pages** — бесплатный хостинг статических сайтов из репозитория.
- **Releases** — публикация готовых версий проекта с прикреплёнными файлами.
- **Projects** — доска задач (канбан) для командной работы.
- **Fork** — своя копия чужого репозитория, из которой отправляют pull request автору. Так принято вносить вклад в открытые проекты.

**Общее**

- **Приватные репозитории** — удобны для учебных работ, которые нельзя выкладывать публично. Чтобы преподаватель мог проверить, добавьте его в участники (collaborators) репозитория.

> К ИИ-ассистентам относитесь как к подсказке, а не как к источнику истины: проверяйте и понимайте то, что вставляете. Если на курсе нужен отчёт об использовании ИИ, указывайте и их тоже.

### GitVerse и GitHub: сравнение

|  | GitVerse | GitHub |
| --- | --- | --- |
| Кто делает | СберТех (Сбер) | Microsoft |
| Размещение | Россия | США |
| Команды Git | те же | те же |
| Аутентификация | SSH-ключ или токен | SSH-ключ или Personal Access Token |
| Запрос на слияние | pull request | pull request |
| Задачи | Issues | Issues, Projects |
| Автосборка | встроенный CI/CD (свой формат) | GitHub Actions (YAML) |
| ИИ-помощник | GigaCode | Copilot |
| Сайты из репозитория | GitVerse Pages | GitHub Pages |
| Консольная утилита | нет единого аналога `gh` (проверьте документацию) | `gh` |

Если сомневаетесь в какой-то ячейке таблицы, проверьте актуальную документацию: у обеих платформ функции быстро меняются.

## 13. Правила сдачи учебных работ

Согласуйте конкретные требования с преподавателем. Обычно:

1. Один репозиторий на студента (или на команду), понятное имя, например `cpp-practicum-1-иванов`.
2. В корне лежит `README.md`: кто автор, как собрать и запустить, структура папок.
3. Нет бинарников и папок сборки (проверьте `.gitignore`).
4. История коммитов осмысленная и отражает ваш ход работы, а не один коммит «всё» в последнюю ночь.
5. Если использовали ИИ, оформите отчёт по правилам курса.
6. Репозиторий приватный, преподаватель добавлен участником, либо ссылка передана в оговорённом виде.

**Чек-лист перед сдачей:**

- [ ] `git status` чистый, всё закоммичено
- [ ] `git push` выполнен, на GitVerse видны последние изменения
- [ ] проект собирается из свежего клона (`git clone` в другую папку и сборка)
- [ ] в репозитории нет паролей, токенов и мусорных файлов
- [ ] README заполнен

## 15. Типичные ошибки новичков

1. **Коммит папки `build/` и `.exe`.** Решение: `.gitignore` с самого начала.
2. **«Я закоммитил, но на сайте пусто».** Забыли `git push`.
3. **`git push` отклонён (rejected).** На сервере есть изменения, которых нет у вас: сначала `git pull`.
4. **Работа прямо в `main`** в командном проекте. Всегда создавайте ветку.
5. **Ошибка прав доступа (Permission denied).** Не добавлен SSH-ключ или неверный адрес репозитория.
6. **Коммиты одним огромным куском** с сообщением «исправления». Делайте маленькие осмысленные коммиты.
7. **Путаница в авторстве.** Не настроены `user.name`/`user.email`.
