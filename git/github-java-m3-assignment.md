# GitHub на паре: Java — задание по трём ролям

Перед началом выполните [настройку компьютера](github-java-m3-setup.md).

## Доступ к репозиторию

Примите приглашение в свой именной репозиторий с правом Admin. В нём вы будете аналитиком и добавите разработчика и ревьюера с правом Write. Чтобы работать в чужом репозитории, примите приглашение от его аналитика.

## 1. Что вы будете делать

Для первого этапа каждому студенту выделен **именной репозиторий** в организации Flovwvers-students. Все стартовые проекты одного языка одинаковы: калькулятор со сложением и вычитанием. Каждый проходит три роли — аналитик, разработчик, ревьюер — вместе с двумя одногруппниками.

Адрес своего Java-репозитория возьмите из таблицы группы. Не угадывайте транслитерацию имени в адресе.

### Как организовать три роли

Найдите свою команду в таблице группы. У каждого есть именной репозиторий. Пример распределения для трёх участников A, B и C:

| Репозиторий | Аналитик и администратор | Разработчик | Ревьюер |
|---|---|---|---|
| Репозиторий A | A | B | C |
| Репозиторий B | B | C | A |
| Репозиторий C | C | A | B |

Используйте распределение ролей из таблицы группы. Таблица выше показывает пример ротации: каждый должен пройти все три роли.

Можно выполнять три репозитория по очереди с ротацией или идти по этапам: все создают задачи как аналитики, все реализуют чужую задачу как разработчики, затем все проверяют чужой PR. В результате каждый сделал один полный набор действий в каждой роли. Если группа не делится на три, согласуйте с преподавателем участие одного человека в двух командах; автор кода и его ревьюер всегда разные люди.

### Права и самостоятельное добавление команды

Убедитесь, что получили **Admin** в своём именном репозитории. Это право действует только в нём.

После получения Admin студент-аналитик сам приглашает разработчика и ревьюера с правом **Write** через Settings → Collaborators and teams → Add people. Разработчик и ревьюер принимают приглашения, после чего начинают работу.

Работайте через ветку и Pull Request. Не меняйте настройки защиты main. Слияние выполняет ревьюер только после полного цикла доработки и проверки.

## 2. Аналитик: собрать команду и создать Issue

1. Откройте свой именной репозиторий. Найдите разработчика и ревьюера по распределению группы и узнайте их точные GitHub-логины.
2. Откройте **Settings → Collaborators and teams → Add people**, найдите разработчика по логину, выберите **Write** и отправьте приглашение. Повторите для ревьюера. Название раздела может отображаться как Collaborators или Manage access. Если политика организации запрещает приглашать внешних участников, попросите преподавателя сначала добавить их в организацию; затем пригласите их в свой репозиторий сами.
3. Дождитесь, пока оба примут приглашения. Проверьте список collaborators. Если нет Settings или Add people, преподаватель ещё не выдал вам Admin. Admin даётся только вам в вашем репозитории; команде для разработки и проверки достаточно Write.
4. Откройте репозиторий → **Issues → New issue**. Если предложен шаблон, выберите **Open a blank issue**.
5. Заголовок: `Добавить умножение в калькулятор`. Вставьте описание:
	 
```markdown
## Контекст
В калькуляторе уже есть сложение и вычитание. Нужно добавить умножение.

## Критерии приёмки
- [ ] В src/Calculator.java есть публичный метод multiply(int left, int right), возвращающий int.
- [ ] multiply(5, 3) = 15; multiply(0, 7) = 0; multiply(-2, 3) = -6.
- [ ] При запуске показана строка 5 * 3 = 15.
- [ ] Строки Calculator, 5 - 3 = 2 и 5 + 3 = 8 сохранены.
- [ ] Проект собирается без ошибок.

## Границы задачи
Только небольшие целые числа. Деление, дроби и переполнение не входят в задачу.
```
 
6. Справа **Assignees** → выберите выбранного вами разработчика этого репозитория. При наличии метки выберите `enhancement`. Если нет Assignees или нужного логина, проверьте права с преподавателем.
7. Нажмите **Submit new issue**. Сообщите разработчику ссылку и номер (например, #1).

## 3. Разработчик: ветка и код

1. Откройте назначенное Issue в **чужом** репозитории, прочитайте критерии, напишите «Беру в работу».
2. Скопируйте HTTPS-адрес через **Code → Local → HTTPS**. В командах ниже показан пример; замените его на репозиторий, где вы разработчик.

На университетском ПК сначала выполните блок личного диска из [файла настройки](github-java-m3-setup.md) в этом терминале. На собственном Windows-ноутбуке вместо `Set-Location $UniversityGithub` используйте `New-Item -ItemType Directory -Force "$HOME/github" | Out-Null`, затем `Set-Location "$HOME/github"`; в CMD вместо пути переменной — `if not exist "%USERPROFILE%\github" mkdir "%USERPROFILE%\github"`, затем `cd /d "%USERPROFILE%\github"`. Остальные команды clone и создания ветки одинаковы.

PowerShell:

```powershell
Set-Location $UniversityGithub
git clone https://github.com/Flovwvers-students/java-calculator-belyakov-aleksey.git
cd java-calculator-belyakov-aleksey
git switch -c feature/multiplication
```

CMD:

```bat
cd /d "%UniversityGithub%"
git clone https://github.com/Flovwvers-students/java-calculator-belyakov-aleksey.git
cd java-calculator-belyakov-aleksey
git switch -c feature/multiplication
```

Linux/macOS:

```sh
mkdir -p "$HOME/github-training"
cd "$HOME/github-training"
git clone https://github.com/Flovwvers-students/java-calculator-belyakov-aleksey.git
cd java-calculator-belyakov-aleksey
git switch -c feature/multiplication
```

Если уже клонировали этот репозиторий, откройте его папку, проверьте `git status`, переключитесь `git switch main`, выполните `git pull --ff-only` и создайте ветку. Не клонируйте поверх существующей папки.

### Готовое решение для первого упражнения

Откройте указанные файлы редактором и замените содержимое. В стартовом калькуляторе есть сложение и вычитание; умножение добавляете вы.

src/Calculator.java:

```java
public class Calculator {
    public int add(int left, int right) { return left + right; }
    public int subtract(int left, int right) { return left - right; }
    public int multiply(int left, int right) { return left * right; }
}
```

src/Main.java:

```java
public class Main {
    public static void main(String[] args) {
        Calculator calculator = new Calculator();
        int left = 5;
        int right = 3;
        int product = calculator.multiply(left, right);
        System.out.println("Calculator");
        System.out.println(left + " - " + right + " = " + calculator.subtract(left, right));
        System.out.println(left + " + " + right + " = " + calculator.add(left, right));
        System.out.println(left + " * " + right + " = " + product);
    }
}
```

### Сборка и запуск из корня проекта

PowerShell:

```powershell
javac -d out src/Calculator.java src/Main.java
java -cp out Main
```

CMD:

```bat
javac -d out src/Calculator.java src/Main.java
java -cp out Main
```

Linux/macOS:

```sh
javac -d out src/Calculator.java src/Main.java
java -cp out Main
```

Выполняйте запуск только после успешной сборки, чтобы не проверить старый исполняемый файл.

Ожидается:

```text
Calculator
5 - 3 = 2
5 + 3 = 8
5 * 3 = 15
```

Проверьте также 0 и отрицательное число: временно поменяйте left/right в Main, соберите и запустите, затем верните 5/3 и повторите сборку. Не проверяйте огромные значения: в Java int переполняется, в C++ переполнение знакового int не определено.

### Commit и push

Во всех оболочках одинаково:

```sh
git status
git diff
git add src/Calculator.java src/Main.java
git commit -m "Add multiplication"
git push -u origin feature/multiplication
```

В `git status` не должны появиться out и исполняемые файлы: они исключены `.gitignore`. В коммит добавляйте только исходники.

## 4. Разработчик: открыть Pull Request

1. На GitHub откройте **ваш рабочий репозиторий** → **Compare & pull request** (или Pull requests → New pull request).
2. Убедитесь: `base: main`, `compare: feature/multiplication`, организация `Flovwvers-students`.
3. Заголовок: `Добавить умножение`. Описание (замените номер):

```markdown
Closes #1

## Что сделано
Добавлены multiply и вывод примера умножения.

## Проверка
Проект собран и запущен; 5*3=15, 0*7=0, -2*3=-6.
Сложение и вычитание сохранены.

## Ограничения
Переполнение не обрабатывается, как оговорено в Issue.
```

4. В **Reviewers** выберите согласованного с командой ревьюера, а не себя и не аналитика.
5. Нажмите **Create pull request**. Передайте ревьюеру ссылку. Не нажимайте Merge до проверки.

## 5. Ревьюер: сначала Request changes, затем исправление и Approve

**В первом упражнении нельзя сразу ставить Approve и нажимать Merge. Сначала обязательно пройдите учебную доработку.** Порядок один:

**Request changes → исправление разработчиком → push в тот же PR → повторное ревью → Approve → Merge.**

### Шаг 1. Проверить чужой PR

1. Откройте PR, затем связанное Issue и вкладку **Files changed**. Сверьте критерии приёмки.
2. Проверьте, что multiply действительно умножает, сложение и вычитание сохранены, нет out, `.class` и посторонних файлов.
3. Для проверки на компьютере клонируйте репозиторий в отдельную папку на личном сохраняемом диске. Выполните `git fetch origin`, затем `git switch --track origin/feature/multiplication`. Если разработчик назвал ветку иначе, используйте точное имя из PR. Если локальная ветка уже есть, `git switch ИМЯ-ВЕТКИ`, затем `git pull --ff-only`.
4. Соберите и запустите программу по разделу разработчика. Проверьте 5/3, 0/7 и -2/3. Временные изменения для проверки верните редактором; не коммитьте их за разработчика.

### Шаг 2. Первый review — Request changes

Даже если код работает, в этом упражнении нужен заранее оговорённый учебный запрос на доработку. Это не утверждение, что рабочий код ошибочен.

1. На **Files changed** нажмите плюс рядом со строкой с `product` и **Start a review**.
2. Напишите: «Учебная доработка: переименуйте product в multiplicationResult в объявлении и использовании, чтобы имя точнее описывало значение».
3. Нажмите **Review changes → Request changes → Submit review**. Одного построчного комментария без отправки review недостаточно. **Approve на этом шаге не выбирайте.**
4. Если в коде уже `multiplicationResult`, запросите небольшое осмысленное улучшение, например добавить понятную подпись к выводу результата. Не просите специально ломать код или возвращать исправление обратно.

### Шаг 3. Разработчик исправляет тот же PR

Разработчик меняет `product` на `multiplicationResult` во всех соответствующих местах `src/Main.java`, повторяет сборку и проверки, затем выполняет в своей рабочей ветке:

```sh
git status
git diff
git add src/Main.java
git commit -m "Clarify multiplication result name"
git push
```

Исправление автоматически появляется в **том же PR**. Новую ветку и новый PR для обычного ответа на замечание создавать не нужно. Разработчик отвечает на замечание и нажимает **Re-request review**, если кнопка доступна; иначе сообщает ревьюеру ссылку на обновлённый PR.

### Шаг 4. Повторный review — Approve

1. Ревьюер проверяет **новый коммит и diff**, убеждается, что запрос выполнен, повторно собирает и запускает программу.
2. Если не исправлено — снова объясняет, что осталось сделать. Одобрять пока нельзя.
3. Если исправлено — отмечает обсуждение **Resolve conversation**, затем **Review changes → Approve → Submit review**. Пример текста: «Замечание исправлено. Проверены 5×3=15, 0×7=0, -2×3=-6; сложение и вычитание сохранены».
4. Только теперь переходите к merge в следующем разделе. Если PR — **Draft**, разработчик сначала нажимает **Ready for review**.

### Если уже нажали Approve, закрыли или слили PR

- **Approve есть, PR открыт:** отправьте новый review с Request changes, затем выполните исправление и повторный Approve. Предыдущее одобрение не завершает упражнение.
- **PR закрыт без merge:** попробуйте Reopen pull request; при удалённой ветке — Restore branch, если доступно. Если восстановление недоступно, сохраните работу и согласуйте новый PR с преподавателем.
- **PR уже слит:** заново открыть его нельзя. Создайте ветку от актуального main и новый PR с небольшой доработкой; на нём пройдите Request changes → исправление → Approve → Merge. Отменять рабочий результат ради учебного цикла не нужно. В новом PR дайте ссылку на прежний, чтобы преподаватель сопоставил действия.
- **Код отправлен сразу в main:** остановитесь и попросите преподавателя помочь создать отдельный учебный PR без потери кода. Не делайте reset/force-push наугад.

## 6. Merge, закрытие Issue и уборка

1. Ревьюер открывает Conversation. В истории уже должны быть Request changes, новый коммит с исправлением и последующий Approve. Все обсуждения решены, конфликтов нет, PR не Draft. Если этого нет, вернитесь к этапу доработки.
2. Нажимает **Merge pull request → Confirm merge** (если доступен Squash and merge, он тоже допустим).
3. Удаляет удалённую ветку через **Delete branch**.
4. Аналитик проверяет Issue: должно стать **Closed** после merge в main благодаря `Closes #номер`. Если этого не произошло, проверьте ссылку и номер и закройте задачу после проверки результата.
5. Разработчик выполняет:

```sh
git switch main
git pull --ff-only
git fetch --prune
git branch -d feature/multiplication
git log --oneline --graph --all
```

После squash Git иногда отказывается удалить локальную ветку через `-d`. Сначала убедитесь по GitHub и diff, что вся работа вошла в main; только тогда можно удалить конкретную учебную ветку через `git branch -D feature/multiplication`. Не удаляйте ветку с несохранённой работой.

Если push отклонён из-за чужих изменений, сначала `git fetch`, прочитайте сообщение, согласуйте изменения с преподавателем. Не используйте force-push. При конфликте в PR разработчик в своей ветке делает `git fetch origin`, `git merge origin/main`, исправляет отмеченные участки, собирает программу, делает commit и push; затем нужна новая проверка.

## 7. Чек-лист завершения

- [ ] Как аналитик создал понятное Issue и назначил разработчика в своём репозитории.
- [ ] Как разработчик создал ветку, собрал проект, сделал commit/push, открыл PR, исправил замечание новым коммитом в том же PR.
- [ ] Как ревьюер сначала отправил Request changes, дождался исправления новым коммитом, повторно проверил, отправил Approve и выполнил Merge. Один Approve без остальных шагов не завершает роль.
- [ ] В каждом репозитории умножение в main, Issue закрыто, исходники сохранены.

Перед выходом из университетской сессии выполните `git status`, сохраните нужные изменения коммитом и отправьте свою рабочую ветку через `git push`. Проверьте коммит на GitHub. При первом использовании личного диска после повторного входа убедитесь, что папка проекта и `.git` сохранились. Не удаляйте локальную работу при ошибке сети. После входа повторите выбор диска, `GIT_CONFIG_GLOBAL`, проверку программ и при необходимости авторизацию/диагностику прокси. Не считайте браузерные настройки сохранёнными автоматически.

## 8. Частые затруднения

| Симптом | Решение |
|---|---|
| Нет нужного Assignee/Reviewer | Проверить логин, принятие приглашения и права в конкретном репозитории |
| Нет Compare & pull request | Проверить успешный push ветки; открыть Pull requests → New pull request |
| Нет Merge / merge заблокирован | Прочитать причину: review, обсуждения, конфликт или права; исправить причину |
| main отклоняет push | Работать в feature-ветке и создать PR |
| javac не найден | Проверить установку, Path и перезапуск терминала |
| destination path already exists | Открыть уже клонированную папку; не удалять её автоматически |
| Непонятный timeout/407/сертификат | Выполнить диагностику в файле настройки и передать преподавателю ошибку без секретов |
