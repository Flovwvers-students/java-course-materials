# Командная практика GitHub

## Самостоятельная командная практика GitHub

Разберитесь в программе, прочитайте легенду своей задачи из списка ниже и проверьте жалобы пользователей. Это практическое задание.

Проверьте каждую жалобу: воспроизведите проблему, сформулируйте ожидаемый результат и объясните её причину. Несколько жалоб могут быть вызваны одной ошибкой. Если сборка пока не проходит, после её исправления продолжите проверку поведения программы. Не ограничивайтесь успешной компиляцией.

### Организация работы

Самостоятельно организуйте работу через Issue, отдельные ветки и Pull Request. Каждый участник должен побывать аналитиком, разработчиком и ревьюером. Распределение участников сообщает преподаватель на занятии.

Аналитик описывает проблему или требуемую проверку: условия воспроизведения, ожидаемое и фактическое поведение, критерии готовности. Разработчик выполняет согласованную работу, проверяет результат и объясняет изменения в PR. Ревьюер самостоятельно проверяет код и поведение, оставляет содержательный отзыв и принимает решение по результату проверки.

Исправляйте подтверждённые недостатки. Добавление воспроизводимых проверок и документирование результата также являются осмысленными задачами. Не создавайте пустые Issue, коммиты или PR ради количества. Если объём работы оказался меньше ожидаемого, согласуйте оставшуюся задачу с преподавателем.

### Что должно остаться в GitHub

- Issue с понятной постановкой и критериями готовности.
- PR со связью с Issue и объяснением причины проблемы, внесённых изменений и проверки.
- Проверочные примеры: вход или действие, ожидаемый и фактический результат, способ повторить проверку.
- Содержательный review другого участника. При реальных замечаниях — Request changes, новые изменения разработчика и повторная проверка. При отсутствии замечаний — Approve; специально добиваться отказа не требуется.
- В итоговом README — назначение программы, фактические команды сборки и запуска, результаты проверок, известные ограничения и краткий отчёт об использовании ИИ, включая вариант «не использовал».

Изменения в main проводите через PR после чужого одобрения. Автор не одобряет и не сливает собственный PR; после проверки слияние выполняет ревьюер. Исправления после замечаний добавляйте в ту же ветку и тот же PR. Эта практика отличается от сдачи лабораторных, где Merge выполняет преподаватель.

На защите каждый объясняет свою постановку, изменения и замечания к чужому решению. Оцениваются работоспособность, доказательства проверки и осмысленность действий в GitHub.

Пошаговых команд Git и списка ошибок здесь нет: выберите рабочий порядок действий самостоятельно. Если нужен технический справочник по настройке, используйте ранее выданную памятку.
